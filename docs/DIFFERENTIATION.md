## 二、与 moonecho 的边界：两个学科，不是一个

生态中已有 `moonecho` 做声纹识别。它与本项目最容易被混淆——因为两者都处理音频。
但这是两个不同的学科，对象、方法和生态位都不同。

| 维度 | moonecho（声纹识别） | roomacoustics（本项目） |
|---|---|---|
| **回答的问题** | 这是什么声音 | 这房间是什么声学特性 |
| **输入** | 任意录音片段 | 房间的脉冲响应（ISO 3382 规定的测量信号） |
| **输出** | 媒体身份匹配 | RT60 / EDT / T20 / T30、模态频率与衰减 |
| **时间尺度** | 音频内容本身（数秒） | 指数衰减包络（整个余响过程） |
| **信号前提** | 内容决定身份 | 信号已知，只测空间响应 |
| **核心方法** | 星座图指纹 + 倒排索引 + 片段对齐 | Schroeder 能量累积积分 + 区间直线拟合 + 波动方程解析解 |
| **参照标准** | Shazam 类 | ISO 3382 类 |
| **可比指标** | 识别准确率 | RT60 测量不确定度、噪声底裕度 |

**关键区分**：声纹识别看**内容**，房间声学听**空间**。
前者的输入是不可控的（任意录音），后者的输入是严格规定的测量信号——
这个差别决定了两者的算法不可能重合。

**量化**：moonecho 4884 行源码中，房间声学术语命中数为 **0**。

## 四、边界：不声称 WAV 解析，不声称 FFT

这是主办方明确要求，也是本项目主动设定的边界。

| 环节 | 谁做 | 本项目的关系 |
|---|---|---|
| WAV 容器解析 / PCM 解码 | `Ridge-Lab/moonwavkit@0.1.3` | **依赖**，不实现 |
| FFT / 功率谱 | `MoonSpectrum` | **依赖**，暂未接入 |
| Schroeder 能量衰减曲线反演 | 本项目 | ✅ 原创实现 |
| EDT / T20 / T30 拟合 | 本项目 | ✅ 原创实现 |
| Sabine 解析估算 | 本项目 | ✅ 原创实现 |
| 矩形房间模态频率闭式解 | 本项目 | ✅ 原创实现 |

**措辞规范**：
- ✅ "基于脉冲响应计算 RT60"
- ✅ "用 `Ridge-Lab/moonwavkit` 读取 WAV 得到采样点，再计算 RT60"
- ✅ "基于 `MoonSpectrum` 的频谱做模态交叉验证"
- ❌ "提供 WAV 解析能力"
- ❌ "内置 FFT 实现"

**依赖分层的实际落点**（不是口头声明）：
核心库 `haiou/roomacoustics` 的 `moon.pkg` 里**没有** moonwavkit；
它只接受 `Array[Double]` 与采样率，因而不绑定任何数据源。
WAV 读取在 CLI 层（`cmd/main/wav_input.mbt`，约 60 行）。
也就是说"不提供 WAV 解析"这件事在文件结构上可见，不只是 README 里的一句话。

**为什么边界是加分项**：官方验收标准明确写"更看重清晰边界"，
"重复提交、拆分项目或仅做简单修改，不计入验收与奖励"。
把依赖说清楚比把功能说多更符合评审偏好。

## 六、答辩问答预演

**Q：声纹识别不也能算混响时间吗？**
A：不能。声纹识别的输入是任意录音，其目标是内容指纹匹配；
混响时间需要的是 ISO 3382 规定的测量信号，且输出的是**空间特性**而非内容身份。
即使拿到一段带混响的音乐，混响时间是那段录音的属性，不是那个房间的属性——
除非录音是在房间里现场录制且位置固定，这已经超出声纹识别的设计范围。

**Q：这不就是套公式吗？**
A：三个公式确实都是闭式解，但难点在**边界处理**：
噪声底会让 T20 失真达 746%（见 NOTES.md 坑 2），
评价区间必须按 ISO 3382 校验有效性并显式告警；
Sabine 假设完全扩散场，房间越大偏差越大；
模态频率在长边房间会低到人耳范围以下。
把"什么情况下这个数字不可信"讲清楚，比把数字算出来更难。

**Q：依赖了两个库，原创度够吗？**
A：依赖只覆盖**字节流到采样点**和**频域变换**这两步通用基础设施。
本项目做的是从采样点到声学参数的全部计算。
类比：用 FFT 库不代表你是频谱分析项目。
