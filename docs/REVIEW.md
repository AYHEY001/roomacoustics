检查日期：2026-10-13
检查范围：代码、测试、文档、依赖、合规、比赛验收标准符合度

## 一、总体判断

**工程底子是扎实的**：核心算法有测试有效性验证、物理验证有独立探针、
CI 全绿、两个守卫脚本（分层 + 文档数字）让关键约定不靠自律。
按比赛验收六条标准逐条对照，**五条完全满足，一条有明确缺口**。

**但存在一个结构性问题**：

> 测试覆盖集中在核心库（1186 行，未覆盖仅 11 行），
> 而 CLI 层（1279 行，占代码一半）**几乎没有测试覆盖**。
> `main.mbt` 单文件 116 行未覆盖 —— 输入解析、参数读取、输出格式化三层全空。

这个盲区已经产生了实际后果：CLI 参数校验有 3 处缺陷，
其中一处**直接违反项目自己的核心主张**。

## 三、发现的问题（按严重度排序）

### P0：`sabine` 子命令在非法输入下报出错误数字

**这直接违反项目的核心主张。**

```
$ moon run cmd/main -- sabine --length abc --alpha 0.2
房间尺寸  0.00 × 4.00 × 2.60 m
体积      0.00 m³
RT60      0.000 s          ← 报了一个看起来合法的错数字
```

对比：`alpha=0` 时函数正确返回 `None` 走「无法计算」分支
（`roomacoustics.mbt:15` 判断了）。**说明校验逻辑在库里，是 CLI 层没传对**——
`opt_double` 把解析失败的 `abc` 静默变成 `0.0`（`main.mbt:122-124`）。

同一问题在 `modes` 子命令表现为静默空输出：

```
$ moon run cmd/main -- modes --length abc --count 3
房间尺寸  0.00 × 4.00 × 2.60 m
频率 (Hz)  (nx,ny,nz)  类型
--------  ----------  ----
（空表）
```

README 卖点是「结果不可信时明确说不可信，而不是照报一个错数字」。
**这里恰好照报了一个错数字**，而且是用户最容易触发的路径（参数打错字）。

**为什么值得优先修**：如果评委用 `--length abc` 或任何笔误试一下，
会直接撞上项目最想证明自己避开的那个毛病。

**状态：已修（`git log` 见提交「ARGV 参数校验」）。**
修法是让 `parse_double` 能失败（返回 `Option`），参数解析失败即报错退出，
并给三个子命令共用一套尺寸/吸声系数校验。

⚠️ **一处如实修正**：最初以为可以「以非零退出码退出」，
但核心库没有提供设置退出码的 API（`@env` 只读参数），
wasm 目标下也没有对应机制。所以**目前只是打印错误信息，退出码仍是 0**。
对「不报错数字」这个目标来说够了；自动化脚本里判成败会不准，
这是当前实现的已知限制。

### P2：`list_modes` 注释与实现不符

`roomacoustics.mbt:80-81` 注释写：

> 排序时把原序号一并并入比较键 —— `Array::sort_by` 是不稳定排序，
> 只按频率比时频率相同的模态顺序不保证，输出会不可复现。

**但代码只按 `freq` 比较**，没有并入原序号：

```moonbit
indexed.sort_by(fn(a, b) {
  if a.freq < b.freq { -1 } else if a.freq > b.freq { 1 } else { 0 }
})
```

**实测验证**（立方体房间 3×3×3 m，57.17 Hz 三度重合、127.83 Hz 六度重合）：
当前输出保持了插入顺序，看起来没问题。

进一步实测 `sort_by` 的稳定性 —— 4096 个全等键、500 元素分组同键，
**都保持原序**。所以在当前 MoonBit 版本上「不稳定排序」这个前提不成立。

**性质**：注释描述了一个防御措施，代码没实施，而该防御在当前实现下不必要。
不是 bug，但是**注释与代码不符**，且 `found.copy()`（`roomacoustics.mbt:132`）
是多余的复制（`found` 之后不再使用）。可以改成直接排序并修正注释。

### P3：`moon.mod` 的 `repository` 为空

```toml
repository = ""
```

比赛强调「公开仓库」与实际质量可追踪。这是模块元数据里的实际缺口，
mooncakes 发布时会体现。填上仓库地址即可。

### P3：pre-commit hook 未启用

`.githooks/pre-commit` 存在，内容只有一行 `moon check`。
但 `git config core.hooksPath` 无输出 —— **hook 没生效**。
而且即便启用也只跑 `check`，没跑 `test` / `fmt`。
（CI 是最后防线，所以实际风险低。）

### P3：`require_margin_db` 参数从未被使用

`decay.mbt:65-66` 的 `Some(m) => m` 分支未覆盖 ——
这个「评价区间须低于噪声底 N dB」的可配置阈值，
设计了、导出为公开 API，但没有任何测试或调用方用过。
要么补测试，要么考虑这个参数是否真需要暴露。

### P3：`parse_double` 不处理科学计数法与非法输入

`main.mbt:parse_double` 手写解析，遇到 `1e5` 会返回 `1.0`（遇 `e` 停止），
`inf` / `nan` 返回 `0.0`。目前 CLI 参数都是简单数值，影响有限，
但与 P0 同源 —— 都是「静默返回 0.0」这个设计。

## 四、做得好的地方

值得在答辩时主动讲的部分：

1. **测试有效性验证**：`decay_wbtest.mbt:393` 那条测试专门钉住
   `T20 = 60/|slope|` 的定义，注释里写明「若给出 5.5 s 说明用了旧公式」。
   这是从"看起来等价"的写法里区分真伪的测试。

2. **物理验证与实现分离**：`_probe/physics_probe.py` 独立于实现，
   用 numpy 重算一遍。交叉验证抓出过 23 个峰逐位一致。

3. **守卫脚本带自检**：`check_layering.py` / `check_doc_numbers.py`
   都先喂样本验证尺子本身。文档守卫的自检当场抓出两个真缺陷
   （正则匹配不了真实输出、文档措辞导致抓不到）。

4. **诚实的边界叙述**：`DIFFERENTIATION.md` 的措辞规范
   （"基于 X 计算 Y" 而非 "提供 X"）与代码结构一致，是可核对的。

5. **错误处理的分层**：核心库用 `Result` / `Option` 而非 panic，
   `DecayFailReason` 枚举把失败原因分成四类，CLI 层翻译成人话。

## 七、一句话结论


项目在**算法正确性**这件事上做得比大多数参赛项目扎实 ——
有独立探针、有测试有效性验证、有诚实的错误报告机制。
但它在**输入边界**这件事上有个反差：CLI 层原本几乎无测试，
于是参数解析的静默失败让 `sabine` 报出了项目最想避免的「错数字」。

这个反差本轮已修掉主要部分（参数校验 + 14 条测试）。
补上 CLI 覆盖后，项目的主张才真正自洽。
