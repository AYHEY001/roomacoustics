## 一句话

用 MoonBit 从一段房间脉冲响应算出**混响时间与房间模态频率**，
并且在结果不可信时**明确说不可信** —— 而不是照报一个错数字。

## 解决什么问题

房间声学测量有一个广为人知的陷阱：噪声底会抬高能量衰减曲线（EDC）的尾部，
把拟合区间推进噪声里，让斜率趋近于零。外推到 -60 dB 时，
**同一个房间的混响时间可以从 0.8 s 变成 8.9 s** —— 偏差超过 11 倍，
而计算结果看起来完全正常，没有任何报错。

现有工具大多照样输出这个数字。本项目把 ISO 3382 的要求做成**显式失败**：

```
噪声底    -30.1 dB
T20  不可用：评价区间落进噪声底 (余量 5.1 dB)，结果不可信 —— 建议延长测量或降噪
```

同一份语料，跳过校验会报 `T20 = 8.92s`。真值 0.8 s。

## 做了什么

| 能力 | 实现 |
|---|---|
| 能量衰减曲线反演 | Schroeder 累积积分 |
| 衰减时间拟合 | EDT / T20 / T30，ISO 3382 区间最小二乘，外推 -60 dB |
| 噪声底估计与区间有效性校验 | 以 EDC 峰值为基准，判定结果可信度 |
| 衰减时间外推 | `T = 60/\|slope\|`（三个指标分母都是 60 dB，与截距无关） |
| Sabine 解析估算 | `RT60 = 0.161·V/(S·α)` |
| 矩形房间模态频率 | `f = (c/2)·√((nx/Lx)²+(ny/Ly)²+(nz/Lz)²)` |
| **模态频率的实测交叉验证** | 对 IR 做 FFT 取谱峰，与解析式预测逐个配对 |

最后一项是本项目的核心论证：**解析式算出来的模态，在实测响应里真的存在吗？**
对镜像声源法生成的 5.0×4.0×2.6 m 房间响应做验证，
23 个检测到的谱峰**全部**对应上预测模态，多个偏差在 0.1 Hz 以内：

| 检测峰 | 预测模态 | 偏差 |
|---|---|---|
| 133.91 Hz | 133.95 Hz | -0.04 |
| 297.43 Hz | 297.39 Hz | +0.04 |
| 464.98 Hz | 464.98 Hz | **0.00** |

## 不做什么（边界）

**不提供 WAV 解析，不实现 FFT。** 这两件事交给生态里已有的成熟库：

| 环节 | 依赖 |
|---|---|
| WAV 读取与解码 | `Ridge-Lab/moonwavkit@0.1.3` |
| FFT 与窗函数 | `chgttyyr/MoonSpectrum@0.2.2` |

分层是**可核对**的，不只是声明：核心库 `haiou/roomacoustics` 的
`moon.pkg` 里没有这两个依赖，只依赖标准库的 `math`/`double`/`debug`。
库的接口只接受 `Array[Double]` 采样点与采样率，不绑定数据源；
I/O 与频谱都在 CLI 层。

本项目回答的是"**给定一个房间的声学响应，它意味着什么**"，
而不是"如何把一个字节流变成采样点"。

## AI 参与情况

AI 参与了实现、测试、文档与调试。所有技术选择与结论都经过验证，
关键结论有独立证据：

- 数值正确性靠**双实现对账**：Python 参考实现与 MoonBit 实现
  在同一份语料上给出逐位一致的结果（含 23 个谱峰的频率）
- 每个功能都有**回归测试**，并做过**测试有效性验证**
  （故意注入错误实现，确认对应测试会变红）
- 发现并修正了一个实质性错误：模态公式曾少一个 `1/2`，
  导致频率翻倍、只保留偶数阶模态，配对率卡在 91%。
  对着实测频谱定位后修正，配对率升到 100%。
  全程记录在 `NOTES.md`
